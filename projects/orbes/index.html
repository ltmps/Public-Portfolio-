Test stories

Detail C · Follow the mismatch to a smaller test

Story 1 · State estimation

Yaw aligned. Roll still disagreed.

Hanging tests exposed a camera/IMU frame mismatch. A two-state Kalman test for yaw and body-rate bias isolated the transient before testing returned to all three axes.

Story 2 · Actuation

A command can ask for too much.

Some requests fell outside the thrusters' feasible wrench envelope. Flooring negative fallback commands could leave zero output, so requests were scaled toward feasible commands.

Story 3 · Wireless actuation

A small error asked for nearly full throttle.

I ran the reaction-wheel controller on an ESP32 over UDP and logged every DShot command. The negative half of the PID-to-DShot mapping ran backwards, so an output of −1 sent 1047. I reproduced it offline and wrote a corrected mapping that still needs a bench test.

Story 4 · Communication links

The link moved three times before it held.

I moved the ESP32 link from USB serial to MQTT over TCP, then to raw UDP. On the full vehicle, Wi-Fi reached a 30% packet drop, so I moved the links to wired USB serial with a 15 ms median camera-to-throttle latency.

ROS2 data path and data acquisition

  • Designed a custom ROS2 message that carries IMU data, AprilTag pose, Kalman state, all 14 motor commands and the desired force and torque in one timestamped record, so every subsystem is logged and plotted on the same clock.
  • Built the onboard data acquisition for every run: the IMU logged at about 225 Hz, AprilTag detections at about 23 Hz, the IR camera at about 10 Hz and motor commands at about 15 Hz, with an 86 to 93 channel CSV per run.
  • Wrote a ROS2 replay node that republishes recorded runs at their original timing and detects the 37- and 50-column log formats, so estimator and controller changes could be checked against real sensor data without the hardware.
  • Wrote a ROS2 bridge to the ESP32 motor controllers over USB serial at 115200 baud that sends timed commands and publishes the ESP32 clock, to check timing between the flight computer and the motor controllers.
  • Wrote a C++ RViz panel that plots acceleration, angular rate and Kalman position and velocity live beside the 3D attitude view in Fig. 5.
  • Logged ESC RPM telemetry against DSHOT commands over serial to map each motor command to motor speed.
  • Built the onboard mode launcher on the Raspberry Pi: button and OLED mode selection, ESP32 serial connection and reconnection, zero-throttle shutdown and a system log of every run.

The run logs also caught what the live view missed. In one IR tracking run only one of the two ESP32 motor links connected, and 1,352 commands to the other failed while the run carried on. A run should not start until every motor link answers.

Lessons

Check the estimate, then the command

General notes

  1. Check every axis after a frame correction.
  2. Check what the motors can produce.
  3. Confirm every motor link before a run.
  4. Count dropped packets on every link.
